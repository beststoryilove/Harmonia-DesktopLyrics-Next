# 桌面歌词程序 + TTML（多声部 / 背景人声 / 重叠时间轴）设计文档

- 日期：2026-09-18
- 状态：已实现（测试与验证脚本已落地）
- 位置：`Harmonia-DesktopLyrics-Next/`
- 关联：`Harmonia/js/main.js`（播放器端，已做最小改动打通）

## 1. 背景与目标

`Harmonia/js/main.js` 中早已存在桌面歌词客户端（`connectDesktopLyrics`），它会连接
`ws://localhost:8765?token=…` 并发送三种消息：

```js
{ type: 'song',       song, artist, album }
{ type: 'full_lyric', format, lyric, tlyric, lines: [...] }
{ type: 'time',       currentTime }
```

但源码注释明确写着：**「服务端不在本仓库」**（`main.js:3230`）。因此该功能长期只有客户端
没有对端，且注释同时记录了已知风险：连接无鉴权，本机任意页面都能连上接收播放信息或推送假歌词。

**目标**：实现这个缺失的桌面歌词程序，并要求它完整支持 TTML 的三种进阶形态：

1. **多声部**（`ttm:agent`）——对唱双方各自的声部
2. **背景歌词**（`ttm:role="x-bg"`）——背景人声，与主行并行的独立时间轴
3. **重叠时间轴**——同一时刻多行同时活跃

## 2. 关键设计决策

### 2.1 技术栈：Electron + 自研零依赖 WebSocket 服务端

| 方案 | 取舍 |
|---|---|
| **Electron + 内嵌 WS 服务端（采用）** | 与项目现有桌面端同栈（`HarmoniaApp/源码/desktop` 已是 Electron 33.4.11，本机 `node_modules` 里就有可执行文件）；主进程内嵌服务端，**一个进程搞定**，直接复用播放器端已硬编码的 `ws://localhost:8765`，用户点一下就连上 |
| Electron + 独立服务端进程 | 需多一个常驻进程与生命周期管理，对「桌面歌词」这个单机场景属过度设计 |
| 纯 Web（浏览器窗口） | 无法做成真正的无边框置顶窗口，失去桌面歌词的意义 |
| Tauri / Rust | 体积更小，但需额外工具链，且与项目现有栈不一致 |

**自研 WebSocket 而非依赖 `ws`** 的理由：

- 运行时**零第三方依赖**，Electron 主进程直接可用，打包时无需带 `node_modules`；
- 所需能力只有「文本消息 + ping/pong + close」，`ws` 的完整 API 面属过度引入；
- **鉴权必须在服务端实现**（见 §2.3），自研才能把 Origin 白名单与 token 校验做进握手路径。

### 2.2 协议：向后兼容优先

服务端**完整支持播放器端现有的三种消息**，做到「播放器不改一行也能用」。在此之上新增字段（老播放器不发也不影响）：

| 消息 | 方向 | 说明 |
|---|---|---|
| `song` / `full_lyric` / `time` | 播放器 → 桌面端 | **原有**，原样支持 |
| `full_lyric.ttml` | 播放器 → 桌面端 | **新增**：原始 TTML 原文 |
| `full_lyric.lines[].agent` / `isPriorityBg` | 播放器 → 桌面端 | **新增**：声部标识与副行类型 |
| `ttml` | 播放器 → 桌面端 | **新增**：独立推送原始 TTML |
| `status` / `seek` / `hello` / `ping` | 播放器 → 桌面端 | **新增**：播放状态、跳转、握手、心跳 |
| `welcome` / `ack` / `error` / `pong` | 桌面端 → 播放器 | 握手、确认、错误、心跳回显 |
| `command` | 桌面端 → 播放器 | 回传播放控制（播放/暂停/切歌） |

**为什么必须新增 `ttml` 而不是复用 `lines`**：LRC 序列化无法表达声部与背景人声
（主行与背景行的文本会被串成一行、`agent` 信息丢失）。播放器端原本只发序列化结果，
桌面端再怎么解析也还原不出多声部。因此必须让原始 TTML 直通到桌面端本地解析。

### 2.3 安全：在握手阶段完成鉴权

播放器端注释里的已知风险必须在服务端闭环：

- **Origin 白名单**：未配置白名单时，**拒绝所有带 Origin 的浏览器请求**，仅放行本机进程
  （Node 脚本 / Electron 不发送 Origin 头，网页无法伪造），默认最安全；
- **一次性 token**：支持 `?token=` 校验，用**恒定时间比较**（`timingSafeEqual`）避免计时侧信道；
- `requireToken` 默认关闭——否则会与播放器端「随机 nonce 当 token」的现有行为冲突；
  需要严格模式时用 `HDL_TOKEN` 环境变量开启。

## 4. TTML 解析（核心能力）

`src/core/ttml.js` 覆盖范围（对齐 Apple Music 歌词扩展与 AMLL TTML DB 社区约定）：

| 能力 | 实现要点 |
|---|---|
| **逐字/逐音节时序** | `<span begin end>`；`itunes:timing="Word" \| "Line"` 两种模式 |
| **多声部** | `ttm:agent`（`<p>` 级**与** `<span>` 级）；`<ttm:agent type role>` 元数据 |
| **行内换声部** | 同一 `<p>` 内 `<span ttm:agent>` 换声部时，**按声部切分为独立行**，使对唱能正确分区 |
| **背景人声** | `ttm:role="x-bg"`，拥有**自己的逐字时序**，与主行并行（非包含关系） |
| **重叠时间轴** | **不假设** `<p>` 互不重叠，重叠行全部保留并给出提示 |
| **翻译/音译** | 内联 `x-translation` / `x-roman`；Apple sidecar `<iTunesMetadata><translations><text for="L1">` |
| **Ruby 注音** | `tts:ruby="container\|base\|textContainer\|text"`，容器折叠为单个词并保留注音 |
| **时间格式** | `HH:MM:SS.mmm` / `MM:SS.mmm` / `MM:SS` / `12.3s` / `500ms` / 裸秒数 |
| **段落信息** | `itunes:song-part`（`<div>` 与 `<p>`，经不可枚举的 parent 指针上溯） |
| **空白语义** | 遵循 TTML `xml:space="default"`：词间空白折叠为单空格；行首/行尾空白不算内容 |

### 4.1 空白处理（踩过的坑）

初始实现用「纯空白节点含换行 → 视为排版缩进，忽略」的启发式，结果在**真实 AMLL
样本上把英文歌词的空格全丢了**（`When the hands` → `Whenthehands`）。

真实文件里两种写法并存：

```xml
<!-- 写法 A：空白在 span 之间（美化排版，含换行） -->
<span>When</span>
<span>the</span>
<!-- 写法 B：空白在 span 内部（AMLL DB 实际用法） -->
<span>When </span><span>the </span>
```

因此改为正确的模型：**空白序列一律折叠为单空格并保留**，只有「整行首尾」的空白才剥除；
用一个贯穿递归的 `pendingSpace` 标记表达「待定分隔符」，避免给行首凭空加空格。

## 5. 重叠时间轴调度

`src/core/scheduler.js`。对真实样本（`samples/real-3402223603.ttml`）的统计：

- **34 对**行区间重叠，形态含 `MAIN→BG`、`MAIN→MAIN`、`DUET→BG`、`BG→BG` 等；
- **峰值 4 行同时活跃**（主唱 + 对唱 + 2 条背景人声，@233.56s）。

因此「当前唱哪一行」不是单值查询，而是**带优先级的槽位选择**：

```
主行 fg：普通行最早 → 保持上一次（行间空隙不闪空）→ 对唱行 → 背景行
副行 bg（最多 2 条）：仅对唱/背景行，对唱优先 → 跳过与主行同文本 → 按开始时间排序
                      （单槽位取最新开始者，防早行饿死新行）
```

**性能**：逐帧（60fps）全表扫描不可接受。预建「按 startTime 排序 + 前缀最大 endTime」的
区间索引，查询时二分定位右边界再向左回收，复杂度 `O(log n + k)`。实测 **0.002 ms/帧**
（77 行全曲 15160 帧共 30.8ms），且与朴素全扫描结果**逐点一致**（测试中随机化验证）。

### 5.1 行身份标识（踩过的坑）

`keyOf` 最初用 TTML 的 `itunes:key` 作行标识。但 `itunes:key` 是**段落**标识：
一个 `<p>` 派生出的主行与其背景人声行**共享同一个 key**，于是背景行被「与主行相同」
的判重逻辑整条过滤掉——**背景歌词完全不显示**。

改用「时间区间 + 是否背景行」作为身份后修复。该 bug 只在含 `x-bg` 的样本上暴露，
用真实 AMLL 文件验证时才被发现。

## 6. 播放位置时钟

播放器端 `sendCurrentTimeToDesktop` 有 120ms 节流，而浏览器 `timeupdate` 本身只有约 4Hz，
后台标签页还会被进一步节流。若「来一条 time 就刷新一次界面」，逐字填充会以 120~250ms
为步长跳变，观感是明显卡顿。

因此桌面端做主时钟外推：`显示位置 = 锚点位置 + (现在 − 锚点时刻) × 速率`，
`performance.now()` 单调递增，是理想插值基准。

**校准分级**（`src/core/clock.js`）避免抖动导致进度回跳：

| 偏差 | 动作 |
|---|---|
| ≤ 16ms | 忽略（死区，防微抖） |
| ≤ 120ms | 指数平滑追赶（不产生可见跳变） |
| > 600ms / seek / 换曲 | 硬重锚（此时「追上真实位置」比平滑更重要） |

测试中用「120ms 推送 + 15ms 逐帧读取」模拟真实节奏，断言帧间步长 ≤30ms
（若未做外推会接近 120ms）。

## 7. 部分实现说明

- **`src/server/ws-server.js`**：HTTP Upgrade 握手（含 `Sec-WebSocket-Accept` 计算与
  版本/头校验）、帧解析（FIN/RSV/opcode、7/16/64 位长度、客户端掩码解码）、
  分片重组、ping→pong、close 握手、超长消息与畸形帧防护。
  明确不做扩展协商（permessage-deflate）与 TLS——本机回环连接不需要，且会显著增加攻击面。
- **`src/renderer/karaoke.js`**：行签名变化时才重建 span（同长度复用节点），
  每帧只写 CSS 变量 `--p`（不触发重排），文本宽度仅在换行时测量一次。
  被歌词窗口与离线演示页**共用同一份**，保证「演示所见 = 应用所见」。
- **`src/main/main.js`**：无边框/透明/置顶/跳过任务栏窗口，托盘常驻，
  鼠标穿透，`skipTaskbar`；`/health` 端点额外暴露 `rendererReady` 等状态，
  让外部验证能区分「窗口正常」与「窗口白屏但进程存活」。

## 8. 播放器端最小改动

`Harmonia/js/main.js` 共 5 处改动（全部为**新增字段**，向后兼容）：

1. 新增 `rawTTMLText` 状态；
2. `renderAMLLLines` 按来源维护它——**仅 TTML 来源保留原文，其他格式清空**
   （否则上一次的 TTML 会被误当成当前歌词推送）；
3. TTML 通路传入 `rawTTMLText: ttmlResult.content`；
4. `sendCurrentLyricsToDesktop` 的消息体新增 `ttml`，每行新增 `agent` / `isPriorityBg`，
   每个词新增 `agent`；
5. `displayAMLyrics`（非 TTML 通路）清空 `rawTTMLText`。

**实施方式说明**：`Harmonia/js/main.js` 含字面 NUL 字节
（`lastTitleLyricText = '\0'` 哨兵），通用文件编辑工具会判定为二进制而拒写，
因此改动通过幂等脚本 `scripts/patch-player.mjs` 施加（每处替换都先检测是否已应用）。

### 9.1 逐像素验证为什么必要

「DOM 上有 `--p` 变量」不等于「用户看得见填充」。该脚本取同一个词在 10%/35%/60%/85%
四个进度下的区域截图，测量「最右侧含亮像素的列」：

```
fill=10%  ::after=5.2px   实测前沿=5.0px
fill=35%  ::after=18.3px  实测前沿=18.0px
fill=60%  ::after=31.4px  实测前沿=31.0px
fill=85%  ::after=44.5px  实测前沿=45.0px
```

前沿随进度**单调右移**，直接证明是按宽度裁切而非整词变色；
对照组（`fill=0%` 的词）亮像素为 **0**。

**该脚本踩过的两个坑（已在代码注释中记录）**：

1. 隐藏窗口（`show: false`）的无参 `capturePage()` 返回**空白位图**——合成器不产帧。
   必须用 `capturePage(rect)` 区域截图。
2. 首次区域截图可能拿到**陈旧帧**（管道冷启动），表现为「20% 填充却整词发亮」。
   故每次采样前先做一次预热截图并丢弃。

## 10. 边界情况

- **端口被占用**：启动失败时打印明确指引（`HDL_PORT=<其他端口>`），不静默退出；
- **未解析出歌词行**：返回 `error` 帧而非崩溃；
- **畸形 TTML**：解析器设计上**不抛异常**，脏输入降级为可解析的最优结果并记录 warning；
- **换歌**：清空歌词与时钟，避免上一首残留；
- **多播放器同时连接**：各自独立会话，渲染取 `primarySession()`（按来源优先级 → 行数 → 播放态择优）；
- **已连接但无歌词**：显示「等待歌词…」而非空白窗口；
- **窗口隐藏时**：暂停推送以省电。

## 12. 界面精简与显示修复（2026-09-18 迭代）

### 12.1 背景行「突然出现」

**现象**：新的背景人声行插入时直接蹦出，没有过渡。

**根因**：`.bg-slot` 用 `display: none` → `display: flex` 切换。
`display` 是**离散属性、不可插值**，元素在同一帧内被插入渲染树并以最终状态绘制，
声明在 `opacity` / `max-height` 上的 `transition` 完全不会播放。

**修复**：槽位**常驻渲染树**（收起态 `max-height: 0` + `opacity: 0` + 轻微 `translateY`），
靠可插值属性驱动过渡；多条背景行用 `--slot-index` 错开出现节奏。
另外调整了 JS 顺序 —— **先写内容再加 `is-on`**，否则第一帧是空槽位展开、
随后文字才出现，观感上仍是「跳一下」；并在加类前强制一次样式计算，
确保浏览器以收起态作为过渡起点。

### 12.2 上一句 / 下一句不显示

**现象**：用户反馈从未看到上下句。

**根因（两个独立缺陷叠加）**：

1. **字段位置错位**：主进程把完整行列表写在 IPC 载荷**顶层** `payload.allLines`，
   而渲染层去读 **`view.allLines`**（view 内部）—— 位置不匹配，永远取不到。
   已用探针抓取真实载荷确认：顶层与 view 内都没有 `allLines`。
2. **下发条件过窄**：仅靠 `view.revision !== pushedRevision` 判断。
   若渲染层在 `pushedRevision` 已被置位之后才就绪（窗口重载、歌词先于窗口到达），
   该分支永不触发，`allLines` 一帧都不会下发。

**修复**：渲染层改从载荷顶层读取并缓存；主进程增加
`allLinesPushedToWindow` 标记，保证「本窗口至少收到过一次行列表」；
窗口重建时复位该标记。

同时把上下句 `opacity` 从 `0.30` 提到 `0.46`（0.30 在明亮壁纸上几乎不可见），
并加 `:empty` 折叠 —— 否则首句之前与末句之后会留两行空白，把主行挤离视觉中心。

### 12.3 界面元素精简

按用户要求移除以下常驻元素（它们属于调试/辅助信息，会与歌词争夺注意力）：

| 位置 | 移除项 |
|---|---|
| 顶栏 | 状态文字、徽标、鼠标穿透按钮 `◇`、隐藏按钮 `—` |
| 底栏 | 三个控制按钮（`⏮` `⏯` `⏭`）、进度条、时间显示 |

保留的交互：顶栏 `✕` 退出、**双击标题栏切换播放/暂停**、窗口拖动；
鼠标穿透与窗口隐藏改由**托盘菜单**提供（功能未丢失，只是不再占用窗口空间）。
顶栏与底栏因此只剩「品牌名」与「歌曲信息」两项。

### 12.4 验证方式（含一个仪器教训）

新增 `scripts/verify-bg-fade.mjs` 验证淡入。第一版用 `requestAnimationFrame`
逐帧采样 `opacity`，结果一个中间态都没抓到 —— 看似「过渡没生效」。

**实际是仪器问题**：隐藏窗口（`show: false`）里 Chromium 把 rAF 节流到约 1Hz，
采样间隔变成 1000ms，而过渡只有 340ms，中间态整个落在采样间隙里。

改用 **CSS 过渡事件**（`transitionrun` / `transitionend`）作为主证据 ——
它们由引擎在过渡真实发生时派发，**不受 rAF 节流影响**；同时把窗口设为可见，
逐帧采样才恢复为有效辅助证据。最终同时采到 5 个中间态与 4 个 `transitionend`。

> 本项目中「截图/采样类仪器不可靠」已出现三次（GDI BitBlt 对分层窗口返回白、
> `desktopCapturer` window 源不反映 alpha、rAF 在隐藏窗口被节流）。
> 共同教训：**测量手段本身必须先被校准，否则会把仪器缺陷误判为产品缺陷。**
