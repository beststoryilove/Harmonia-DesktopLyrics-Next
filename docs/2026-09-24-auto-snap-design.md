- 日期：2026-09-24
- 状态：待实施（本文件为设计与验收依据）
- 位置：`Harmonia-DesktopLyrics-Next/`
- 关联：`docs/2026-09-18-desktop-lyrics-ttml-design.md`（歌词渲染与调度主体设计）

## 1. 背景与目标

桌面歌词窗口当前是一个 900×220 的横向浮层，只能靠用户手动拖到任意位置，
不会贴边，也没有竖排形态。用户要求新增**自动吸附**：

> 用户在托盘处开启该功能后，将桌面歌词拖至整个桌面的上/下/左/右的附近，
> 桌面歌词将会自动吸附过去，同时若是吸附在左右的，则桌面歌词变成竖的，
> 不过你需要适配英文歌词。

拆解为四条可验收的目标：

1. 托盘提供「自动吸附」开关，**默认关闭**；开启后才参与吸附；
2. 拖到工作区上/下/左/右附近松手 → 窗口自动贴到该边；
3. 吸附到**左/右**时窗口转为**竖排**形态；上/下保持横排；
4. 竖排必须正确呈现**英文歌词**（不能逐字母竖排），同时不破坏既有的
   多声部 / 背景人声 / 重叠时间轴呈现。

### 1.1 现状：一半已经存在，但完全没接线

`src/core/snap.js`（吸附几何，151 行）与 `src/core/vertical-text.js`（竖排切分，189 行）
**已经实现并且有单元测试**（`tests/snap.test.js` 23 项、`tests/vertical-text.test.js` 28 项，共 51 项）。

但对整个仓库检索 `snap|vertical-text` 的引用可以确认：**没有任何生产代码 import 它们** ——
主进程、preload、渲染层、CSS 全都没有接入。也就是说这两个文件目前是
「写好了算法、通过了单测，但从没被调用过」的状态。

因此本次工作**不是从零新增功能，而是补齐整条装配链路**，
并顺带处理这两个模块周边两处既有的「红」—— 其中一处其实是测试写错，见 §1.2。

### 1.2 两处既有的「红」（基线 253/255）

实施前跑 `npm test` 的基线是 **253/255 通过，2 项失败**，两个失败**恰好都落在本次要用的模块里**：

| 失败用例 | 性质 | 根因 |
|---|---|---|
| `computeSnappedBounds：保持另一轴的中心（不跳到屏幕中央）` | **测试写错**，实现是对的 | 该断言在数学上不可满足，见 §4.3 |
| `英文：缩写点号留在词内`（`splitVerticalUnits('Mr. Smith')`） | **实现写错**，测试是对的 | 得到 `['Mr', '.', 'Smith']`，与模块自己的文档注释「句点缩写（`Mr.`）都应留在词内」直接矛盾。见 §5.3 |

两者性质**相反**，修法也相反 —— 一个改测试，一个改实现。§4.3 与 §5.3 分别给出推导。

**目标验收线：`npm test` 零失败**（含修正这两项），并为新模块补充测试。
注意基线是 **253/255**，而本次会**新增**用例，因此终态计数会大于 255 ——
验收标准是「**失败数为 0**」，不是一个固定的总数。
另外「全绿」不等于「放宽断言」：§4.3 的用例会被**改写为正确的期望值**，
而不是删掉或把容差放大。

## 2. 关键设计决策

### 2.1 触发时机：拖动**结束**时判定，而非 `move` 过程中

| 方案 | 取舍 |
|---|---|
| **监听 `move` 实时吸附（否决）** | `move` 在拖动过程中高频触发。窗口会在用户**还在拖**的时候就被吸走，手感割裂；且吸附改尺寸会再次触发 `move`，存在反馈环风险。 |
| **监听 `moved`（拖动结束）判定（采用）** | 用户松手后才吸附，符合「拖到附近 → 吸附过去」的直觉；每次拖动只判定一次。 |
| `will-move` / `moved` 原生事件 | Electron 在 Windows 上对无边框窗口的 `will-move` 支持不可靠，不作为主依据。 |

**实现约定**：直接监听 `moved` 执行吸附判定。

> **⚠️ 本节初稿设计错了，已按 Task 5 实测更正（保留原推导供后人参考）。**
>
> 初稿写的是「监听 `move` 维护 `isDragging`（200ms 空闲超时兜底），
> `moved` 时若 `isDragging` 为真才判定」——理由是「`moved` 也可能由 `setBounds` 触发」。
>
> **实测（Electron 33.4.11 / Windows）证伪了该前提**：
>
> | 操作 | 实际派发的事件 |
> |---|---|
> | `setBounds` 只改 height | `resize`（**不触发** `move` / `moved`） |
> | `setBounds` 只改 x/y | `move`（**不触发** `moved`） |
> | `setBounds` 同时改位置与尺寸 | `resize` + `move`（**不触发** `moved`） |
> | 真实 OS 鼠标拖动 | `move` ×35，末尾 `moved` ×1 |
>
> **`moved` 只在真实拖动结束时派发一次**，它本身就是精确的「拖动结束」信号，
> 无需被「近似」。那套 200ms 机制因此是多余的，已按 YAGNI 删除。
>
> 另一条仍然成立且必须保留：`setBounds` **会**触发 `move`，所以程序自身改尺寸时
> 必须带 `movingProgrammatically` 守卫，否则拖动预览条会在程序改高度时闪出来。

### 2.2 吸附预览：窗口**内缘**高亮条，不放大窗口

| 方案 | 取舍 |
|---|---|
| **把窗口临时撑大到全屏再画预览（否决）** | 破坏 `getBounds()` 的真实性（`/health` 上报的 `windowBounds` 会失真）；透明窗口一旦全屏会变成整屏拦截鼠标的事件板，用户无法再拖到其他窗口上。 |
| **窗口内缘高亮条（采用）** | 靠近边缘时在**窗口自身内缘**显示一条 3px 高亮条，零几何副作用、零事件副作用，且实现只是切一个 CSS 类。 |

### 2.3 吸附加滞后（hysteresis），两档阈值

触发吸附 **60px**（沿用 `DEFAULT_SNAP_THRESHOLD`），**解除吸附需拖离到 96px 以外**。

若进出用同一阈值，窗口在临界点会反复吸附 / 还原（抖动）。
96px = 60px + 36px 迟滞带，迟滞带宽度取阈值的 60%，足以吸收鼠标抖动的量级。

### 2.4 竖排宽度：按**整首歌**的最大列宽预算，而非当前句

这是本次最关键的一个决策。

竖排是**窄**列。若窗口宽度按「当前这一句」自适应，那么：

1. 窗口宽度会随歌词不断伸缩（英文歌词每 3–4 秒换一句，且句长差异很大）；
2. 窗口伸缩 → 触发 `moved` → 再次进入吸附判定 → **反馈环**；
3. 用户会看到侧边栏持续呼吸式抖动。

因此：**预扫描整首歌的全部行，算出稳定的竖排宽度，在整个会话内保持不变。**

- 数据来源：`session.lines`（`SessionManager` 已持有全部行，含 `words`），
  在歌词版本变化时重算一次，**不在每帧的 `pushState()` 里算**；
- 宽度夹取在 `[MIN_VERTICAL_WIDTH(120), MAX_VERTICAL_WIDTH(320)]`；
- 结果缓存，仅在 `revision` 变化时失效。

## 3. 架构与数据流

```
托盘勾选「自动吸附」
      │  IPC: hdl:setSnapEnabled(enabled)
      ▼
主进程 snapEnabled（同时写入 settings.json）
      │
      │  'move'  → isDragging = true（200ms 空闲超时兜底）
      │  'moved' → decideSnap(bounds, workArea, 60)
      ▼
  decideSnap 命中？
      ├─ 未命中 → 若当前处于吸附态且已拖离 > 96px → 还原横排
      └─ 命中    → computeSnappedBounds(bounds, workArea, edge, size)
                     │  size 由预扫描的 verticalWidth + 工作区高度得出
                     ▼
                 setBounds()  →  窗口贴边 / 变竖排
                     │
                     │  IPC: hdl:layout { mode: 'vertical'|'horizontal', edge }
                     ▼
                 渲染层切 data-layout → LyricPanel 竖排渲染
```

### 3.1 职责边界（延续既有分层）

| 层 | 职责 | 不做 |
|---|---|---|
| `src/core/snap.js` | 吸附几何纯函数 | 不碰 Electron、不碰 DOM |
| `src/core/vertical-text.js` | 文本 → 竖排单元切分 | 同上 |
| `src/core/vertical-layout.js`（新增） | 列宽/列高计算、Y 轴滚动锚点 | 同上 |
| `src/core/settings.js`（新增） | 开关持久化（原子写 + 容错） | 不碰窗口 |
| `src/main/main.js` | 拖动检测、吸附执行、几何落地 | 不做文本切分 |
| `src/renderer/` | 竖排 DOM 与样式、填充 | 不决定窗口几何 |

纯函数全部放在 `src/core/`，因此吸附几何、竖排度量、切分规则都能在
`node:test` 里直接驱动，无需启动 GUI —— 这是本项目既有的一贯做法。

## 4. 吸附几何

### 4.1 判定与阈值

沿用 `decideSnap(bounds, workArea, threshold)`：计算窗口四条边到工作区四条边的距离，
取**距离最小且在阈值内**的那条边；负距离（窗口已部分出屏）也算命中。

使用 `workArea` 而非 `bounds`，保证贴边贴到**可用区域**边缘，窗口不会被任务栏遮住。

### 4.2 尺寸策略

| 吸附边 | 宽度 | 高度 |
|---|---|---|
| `left` / `right`（竖排） | 预扫描的 `verticalWidth`（120–320，夹取） | 工作区高度 |
| `top` / `bottom`（横排） | 还原为**吸附前**的横排尺寸（900×220） | 同左 |

竖排取满工作区高度，因此歌词在整条侧边栏内垂直居中 / 滚动，高度固定不跳动。

### 4.3 一个「实现正确、测试写错」的失败（基线失败项 1）

**初步判断曾经是错的**，这里记录完整推导，避免后来者重复误判。

失败用例：

```js
const bounds = { x: 20, y: 100, width: 900, height: 220 };
const size   = { width: 220, height: 700 };
const result = computeSnappedBounds(bounds, AREA, 'left', size);
const newCenterY = result.y + result.height / 2;
assert.equal(newCenterY, 210);   // ← 失败
```

第一反应是「实现保持了窗口中心而非内容中心」。**实测否定了这个判断**：

```
bounds 中心 y = 100 + 220/2 = 210
吸附结果 = { x: 0, y: 0, width: 220, height: 700 }
结果中心 y = 0 + 700/2 = 350
```

看起来差了 140。但把「保持中心」的**必要条件**写出来就清楚了 ——
要让 700 高的窗口中心落在 210，需要：

```
y = 210 - 700/2 = -140
```

`y = -140` 在工作区 `y ∈ [0, 1080]` 之外，**窗口会有一半跑到屏幕上方去**。
换言之该断言要求的画面，正是同一个测试文件里另一条用例
（`computeSnappedBounds：中心靠边时夹取到工作区内（不出屏）`）明确禁止的：

```js
assert.ok(result.y >= 0, `顶部不应超出，实际 y=${result.y}`);
```

**两条用例互相矛盾，不可能同时通过。**

再验证实现本身在**可满足**的场景下是正确的：

```
bounds.y=400, height=220 → 中心 510
吸附后 y=80, height=700  → 中心 510   ✓ 中心确实被保持
```

因此结论：**`computeSnappedBounds` 的实现是对的**（在「不越界」的前提下尽量保持中心），
错的是那条用例 —— 它给了一个与 clamp 约束冲突的期望值。

**修复**：改写该用例，让它断言**真正应当成立**的性质 ——
「在窗口放得下的位置，中心被保持；放不下时夹取到工作区边界」。
不删除用例、不放宽容差、不改实现。

**对本次功能的影响：无。** 竖排取满工作区高度（§4.2），
此时 `y` 被完全钉死为 `workArea.y`：

```
size = { width: 220, height: 1080 } → { x: 0, y: 0, width: 220, height: 1080 }
```

中心语义在高等于工作区高度时根本不参与计算。所以这条既有缺陷**不阻塞**吸附功能，
但仍要在本次一并修正 —— 否则「零失败」的验收线无法达成。

## 5. 竖排歌词（含英文适配）

### 5.1 切分规则

复用 `splitVerticalUnits`。规则与理由：

| 歌词形态 | 切分结果 | 理由 |
|---|---|---|
| `夜色渐浓`（中文） | `夜` `色` `渐` `浓` | 中文竖排习惯为逐字 |
| `夜が明ける`（日文） | `夜` `が` `明` `け` `る` | 假名与汉字同属 CJK，均逐字 |
| `hello`（英文） | `hello` | **整词**。拆成 `h/e/l/l/o` 竖排完全无法阅读 |
| `We don't talk about Bruno` | `We` / `don't` / `talk` / `about` / `Bruno` | 整词，逐词向下 |
| `don't` / `well-known` | 整块 | 撇号、连字符不断裂 |
| `我 love 你` | `我` / `love` / `你` | 中英混排各自按本语种规则 |

**为什么不用 CSS `writing-mode: vertical-rl`**：该属性在
`text-orientation: mixed` 下会让拉丁字母**旋转 90° 躺倒**，
在 `upright` 下则把拉丁字母也逐字正立 —— 两者都无法同时满足
「中文逐字」与「英文整词横放」。手动切分 + 逐单元布局是唯一可控的方案。

### 5.2 数据基础：TTML 词已经带前导空格且粒度合适

真实样本 `samples/encanto-bruno.ttml`（81 行英文歌词）解析结果：

```json
{"text":"We don't talk about Bruno, no, no, no",
 "words":["We"," don't"," talk"," about"," Bru","no,"," no,"," no,"," no"]}
```

三点结论：

1. **词已按空格切好**，不需要自己实现英文分词 / 断词算法；
2. **前导空格已包含在 `word` 内**（`" don't"`），因此 `splitVerticalUnits`
   的空白处理能正确工作 —— 空白结束当前词且自身不成单元，竖排不需要空格；
3. **但竖排不能直接拿 `line.words` 当单元**：TTML 的切分粒度**比单词还细**
   （`Bru` / `no,` 是为逐字时序服务的音节切分）。原样呈现的话，
   `Bruno` 会被拆成两行且中间断字。
   因此竖排**以 `line.text` 整行文本作为 `splitVerticalUnits` 的输入**
   （它按语种边界重新切分，`Bruno,` → `Bruno` + `,`，`don't` 保持整块），
   再通过 §5.4 的字符偏移映射把时序接回去。

### 5.3 缩写点号缺陷修复（基线失败项 2）

`isLatinWordJoiner` 当前要求连接符**前后都是拉丁字母/数字**：

```js
if (prevIsWordish && nextIsWordish && bufferKind === 'latin') { buffer += ch; }
```

但 `Mr.` 的句点**后面是空格**，`nextIsWordish` 为假，于是被拆成独立标点，
得到 `['Mr', '.', 'Smith']` —— 与模块注释声明的
「句点缩写（`Mr.`）都应留在词内」矛盾。

**修复**：句点（`.`）单独放宽 —— 允许它**留在词尾**（前置为拉丁词即可），
但仍**不允许**它开启一个新词或连续出现，避免 `...` 或行尾句号把整行吞成一个单元。
撇号与连字符维持原有「必须在词中间」的规则不变。

实测的修复前 / 修复后对照（修复前为实际运行结果）：

| 输入 | 修复前（实测） | 修复后（目标） |
|---|---|---|
| `Mr. Smith` | `Mr` `.` `Smith` | `Mr.` `Smith` |
| `U.S.A.` | `U.S.A` `.` | `U.S.A.` |
| `don't` | `don't` | `don't`（不变） |
| `well-known` | `well-known` | `well-known`（不变） |
| `Wait...` | `Wait` `.` `.` `.` | `Wait.` `.` `.` |

**判定规则**：`bufferKind === 'latin'` 且 `buffer` 非空且**不以 `.` 结尾**时，吸收该句点。
于是 `...` 只被吸收一个，其余仍作独立标点 —— 避免省略号被并入单词导致单元宽度异常。
该规则须写入测试（含 `U.S.A.` 与 `Wait...` 两个用例）。

**刻意不改的部分**：逗号、叹号、问号仍独立成单元。
这不是遗漏 —— 既有且**当前通过**的用例已经锁定了这个行为：

```js
splitVerticalUnits('Hello, world!') → ['Hello', ',', 'world', '!']   // 必须保持
splitVerticalUnits('真的吗?')        → ['真', '的', '吗', '?']        // 必须保持
```

竖排里标点独占一格符合竖排排版惯例（`Bruno,` → `Bruno` / `,`），
且真实样本里逗号极常见，改成并词会让单元宽度变大、列更宽。
注意 `vertical-text.js` 顶部的注释「西文标点并入相邻拉丁词」与上述用例**互相矛盾**，
该注释是过时的 —— 本次一并订正注释，以用例为准。

### 5.4 竖排渲染：复用现有卡拉OK 填充机制

**不新造渲染器。** `karaoke.js` 的逐字填充本质是：

> 一个**宽度已知**的盒子 + `overflow: hidden` + `::after` 的 `width: var(--p)`
> 按比例裁剪覆盖层。

横排里盒子是「一个词」；竖排里盒子是「**一列中的一行**」，
填充方向由向右改为**向下**（`height: var(--p)` 而非 `width: var(--p)`）。
填充语义、`--p` 的写入路径、`computeWordFills` 全部复用，因此**竖排仍是真逐字进度**，
不是降级成整行高亮。

**单元 → 时间区间的映射**：`splitVerticalUnits(line.text)` 得到的单元序列，
与 `line.words` 的时序需要对齐。做法是按**字符偏移**建立映射：

- 遍历 `line.words` 时累加字符位置，得到每个 `word` 在 `line.text` 中的 `[start, end)` 区间；
- 再按同一套偏移规则切出竖排单元，每个单元落在某个 `word` 区间内；
- 单元的时间区间 = 所属 `word` 的时间区间**按字符数比例分摊**
  （`t0 + (t1 - t0) * (unitOffsetInWord / wordLength)`）。

这样即使 TTML 的词粒度与竖排单元粒度不一致，逐字填充依然连续且单调。
该映射是纯函数，放在 `src/core/vertical-layout.js` 中单测。

### 5.5 竖排布局：列

按用户选定的方案，**主行 / 每条副行 / 翻译各自成列**，副行弱化：

| 列 | 内容 | 说明 |
|---|---|---|
| 主列 | `view.fg` | 最大字号，最亮 |
| 副列 ×N | `view.bg[]` | 字号更小、透明度更低（沿用横排的 `duet`/`overlap`/`bg` 区分） |
| 翻译列 | `fg.translatedLyric \|\| fg.romanLyric` | 最小字号 |

- 列与列**横向并排**，整体在窗口内居中；
- **列的排布方向固定**，不随吸附边翻转（左吸附与右吸附列序一致），
  避免同一首歌在两侧显示不同，降低认知负担；
- 每列各自独立向下排列、各自独立填充进度。

## 6. 竖排必须滚动（英文长句的硬约束）

真实英文歌词每行 10–15 个词，按一单元一行排下来约 **1200–1500px**，
而竖排窗口高约 1000px（1080 工作区减去任务栏）—— **一屏放不下**。

因此竖排列必须支持**纵向滚动**，且滚动锚点跟随当前唱到的单元：
复用 `KaraokeLine._updateScroll` 的「活跃单元居中」策略，把 X 轴换算成 Y 轴。

这是竖排可用性的前提，不是可选装饰。实现要点与横排一致：

- 单元高度在**重建时测量一次**并缓存，帧循环内不触碰布局；
- 每帧只写 `transform: translateY(...)`，不触发重排；
- 长句时跟随活跃单元滚动，短句时清掉位移并居中。

## 7. 开关持久化

按用户选择，开关状态**记忆到磁盘**。

- 位置：`app.getPath('userData')/settings.json`；
- 内容：`{ "snapEnabled": boolean }`，只存这一个字段（YAGNI，不预埋其他配置）；
- 写入：**原子写**（先写 `settings.json.tmp` 再 `rename`），避免断电 / 崩溃留下半截文件；
- 读取：文件不存在、JSON 解析失败、字段类型不对 → 一律回落 `false`（默认关闭），
  **绝不因配置文件损坏导致启动失败**；
- 时机：`app.whenReady()` 时读取一次，托盘勾选时写入。

**仪器注意（本项目已有三次教训）**：截图 / 采样类仪器不可靠
（GDI BitBlt 对分层窗口返回白、`desktopCapturer` 的 window 源不反映 alpha、
rAF 在隐藏窗口被节流到约 1Hz）。因此：
**像素验证必须在可见窗口中进行**，且优先用引擎派发的事件作为主证据，
逐帧采样只作辅助。

### 9.2 无法自动验证的部分（诚实声明）

**拖动手感无法自动验证。** `scripts/verify-snap.mjs` 用 `setBounds()` 直接摆位置，
它**不经过真实的鼠标拖动事件链**，因此无法验证：

- `move` → `isDragging` → `moved` 这条判定链是否真的被触发；
- 200ms 空闲超时兜底是否会误判（例如窗口被系统移动而非用户拖动）；
- 拖到边缘时的预览条是否在正确的时机出现；
- 96px 迟滞带的手感是否合适。

这些**只能由用户手动确认**。实施完成后的交付说明中会明确列出
「需人工确认」清单，不会把未验证的部分表述为已验证。

## 10. 边界情况

- **吸附开关关闭时**：完全不做任何吸附判定，窗口行为与现状一致；
- **多显示器**：使用窗口**所在显示器**的 `workArea`
  （`screen.getDisplayMatching(bounds)`），而非主显示器，否则副屏上吸附会贴错屏；
- **工作区比竖排窗口还小**（极小分辨率 / 超窄工作区）：
  宽度夹取到工作区宽度，不产生负坐标（`computeSnappedBounds` 已有的 clamp 行为）；
- **窗口已吸附，用户改分辨率 / 拔掉显示器**：窗口可能落到工作区外。
  在 `display-metrics-changed` 时重新夹取到当前工作区内；
- **歌词为空 / 尚未连接**：竖排宽度取 `MIN_VERTICAL_WIDTH`，不抛错；
- **单行歌词只有一个单元**（如 `Hello`）：列高按单元数算，不出现除零；
- **`settings.json` 损坏**：回落默认关闭，不阻塞启动；
- **拖动中切换托盘开关**：以 `moved` 时刻的开关状态为准，不做特殊处理。
